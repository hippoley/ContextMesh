# RAGFlow D24 — context window vs generation output

**Date:** 2026-09-26  
**Upstream:** `infiniflow/ragflow`  
**Pinned current-main commit:** `313ca90f6abd7682fe8523e16fd67b3653a3fa84`  
**Reality status:** confirmed current-main code-path failure

## What was tested

RAGFlow's own OpenAI catalog defines `gpt-4o` with two different limits:

- `context_length = 128000`
- `max_output = 16384`

The probe then followed the current Go chat path rather than inferring semantics from field names.

The current path is:

```text
ModelTarget.ContextLength = 128000
ModelTarget.MaxTokens     = 16384  # chat path derives this from catalog MaxOutput
        |
        v
getLLMModelConfig(... target.MaxTokens ...)
        |
        v
cfg["max_tokens"] = 16384
        |
        v
modelMaxTokens = 16384
        |
        v
messageFitIn(... 0.95 * modelMaxTokens)
```

The executable source probe printed:

```text
CONFIRMED_D24 catalog_context=128000 catalog_max_output=16384 chat_fit_source=target.MaxTokens effective_fit_budget=16384
```

That means the ordinary chat pipeline sizes model-visible input against the **generation-output ceiling**, even though the resolver already carries the separate 128K context window.

At the existing 95% fit factor, that is roughly **15,565 tokens of input budget instead of 121,600** for this controlled catalog case.

## Why this matters to ContextMesh

This is the same failure class as the Cognee rank-17 and Dify hidden-middle probes, but at a different lifecycle stage:

```text
source exists
  -> model route resolves
  -> correct context constraint exists
  -> wrong budget field is selected
  -> otherwise eligible context is trimmed before judgment
```

The important abstraction is not "RAGFlow has a token bug." It is:

> **A correct constraint can exist in state and still become semantically invisible if execution binds the wrong field at the budget boundary.**

That belongs in ContextMesh's verification model as a route/budget binding failure.

## Limits

This is a **code-path proof**, not a live OpenAI request. It pins the upstream commit, verifies the catalog values, and verifies the exact current-main field flow into `messageFitIn`.

A correct upstream fix should keep two constraints separate:

1. context window for prompt/input fitting;
2. maximum generation output for completion limiting.

Simply replacing one value with the other everywhere would trade one semantic bug for another.
